# Сборка прошивки NanoVNA-X

[English version](building.md)

Это руководство описывает воспроизводимый процесс сборки прошивки NanoVNA-X из исходных текстов.
CI и релизные сборки используют официальный пакет Arm GNU 14.2.Rel1 для Linux x86_64
(GCC 14.2.1), включая его библиотеки времени выполнения. Для сравнения размеров
образов используйте тот же пакет в Linux или WSL: пакеты дистрибутивов могут давать
другие результаты даже при совпадении версии GCC.

## 1. Установите необходимые компоненты

NanoVNA-X предназначен для микроконтроллеров семейства ARM Cortex-M, поэтому требуется инструментальная цепочка `arm-none-eabi`, а также утилита Device Firmware Upgrade Utility (`dfu-util`) для прошивки оборудования.

### Ubuntu / Debian

```bash
sudo apt update
sudo apt install build-essential python3 curl ca-certificates xz-utils dfu-util
```

### macOS (Homebrew)

```bash
brew install gcc-arm-none-eabi dfu-util
```

### Windows

Используйте Windows Subsystem for Linux 2 (WSL2 — подсистема Linux для Windows) с дистрибутивом Ubuntu и следуйте инструкциям для Linux, приведенным выше.
Нативная сборка в Windows возможна при использовании архивного дистрибутива Arm GNU toolchain, однако проект проходит тестирование в Unix-подобных средах.

Проверьте доступность компилятора:

```bash
arm-none-eabi-gcc --version
```

## 2. Получите исходный код

Клонируйте репозиторий — все сторонние компоненты (ChibiOS) уже входят в дерево исходников:

```bash
git clone https://github.com/momentics/NanoVNA-X.git
cd NanoVNA-X
```

### 2.1 Структура дерева исходников

Проект перестал быть простым линейным форком (ответвлением) — код распределён по слоям:

| Путь | Назначение |
| --- | --- |
| `include/runtime`, `src/runtime` | Прикладные API верхнего уровня: точка входа, флаги функциональности, координация свипов и консоль. |
| `include/rf`, `src/rf` | Механизм свипирования, измерительный конвейер и сопутствующая аналитика. |
| `include/processing`, `src/processing` | DSP и математические помощники для измерений и UI. |
| `include/sys`, `src/sys` | Общая инфраструктура (конфигурация, планировщик, шина событий, менеджер состояния). |
| `include/driver`, `src/driver` | Драйверы оборудования (LCD, кодек, синтезатор, USB). |
| `include/ui`, `src/ui` | Отрисовка, контроллеры, адаптеры ввода и встроенные ресурсы (шрифты/иконки). |
| `boards/STM32F072`, `boards/STM32F303` | Пакеты поддержки плат, общие с ChibiOS. |

При добавлении функций ориентируйтесь на эти каталоги, чтобы зависимости оставались однонаправленными.

## 3. Выберите целевую платформу

Прошивка собирается для двух аппаратных профилей.
Выберите целевую плату, установив переменную окружения `TARGET` перед запуском `make`:

| Цель | Плата               | Профиль микроконтроллера |
|--------|---------------------|--------------------------|
| F072   | NanoVNA-H (по умолчанию) | STM32F072 |
| F303   | NanoVNA-H4          | STM32F303 |

Если переменная `TARGET` не указана, сборка по умолчанию выполняется для `F072`.

## 4. Соберите прошивку

В Linux x86_64, включая WSL на x86_64, после клонирования установите закреплённый
компилятор:

```bash
bash tools/install-arm-toolchain.sh "$PWD/../arm-gnu-14.2.rel1"
export PATH="$PWD/../arm-gnu-14.2.rel1/bin:$PATH"
```

Установщик проверяет контрольную сумму SHA-256 от Arm перед распаковкой и сверяет
версию компилятора. Версия пакета, версия GCC и контрольная сумма закреплены в
`tools/arm-toolchain.env`. Хеш этого файла включён в ключи кэшей обеих сборочных
процедур, а ключи и резервные префиксы кэша объектов дополнительно учитывают
`Makefile`. Кэши объектов разделены по четырём аппаратным вариантам. При смене
компилятора проверяйте чистые сборки обеих плат и выполняйте `make test`.

Установщик поддерживает только Linux x86_64. Для macOS используйте компилятор
Homebrew, указанный выше; размеры полученных образов могут отличаться.

Оптимизация на этапе компоновки (LTO) включена по умолчанию для F072 и F303:
`USE_LTO=yes`. Её можно явно включить или отключить параметрами `USE_LTO=yes`
и `USE_LTO=no`. Все цели, RF-профили и режимы LTO используют общий каталог
`build/`; Make не отслеживает смену этих параметров автоматически. При смене
платы, RF-профиля, режима LTO или компилятора обязательно выполняйте `make clean`.

Сборка с LTO:

```bash
make clean
make TARGET=F072 USE_LTO=yes -j$(nproc)

make clean
make TARGET=F303 USE_LTO=yes -j$(nproc)
make test
```

Для сборки без LTO сначала очистите объекты и явно укажите `USE_LTO=no`:

```bash
make clean
make TARGET=F072 USE_LTO=no -j$(nproc)

make clean
make TARGET=F303 USE_LTO=no -j$(nproc)
make test
```

Вариант без LTO может не уложиться в бюджет флэш-памяти; проверку компоновщика
нельзя обходить ради получения образа.

В среде macOS используйте `make -j$(sysctl -n hw.ncpu)` для параллельной сборки.

Артефакты сборки размещаются в каталоге `build/`:

- `build/H.elf` / `build/H4.elf` — образ Executable and Linkable Format (ELF — стандартный формат исполняемых файлов) для отладки.
- `build/H.bin` / `build/H4.bin` — двоичный файл для прошивки по Device Firmware Upgrade (DFU — обновление встроенного программного обеспечения через USB).
- `build/H.hex` / `build/H4.hex` — образ в формате Intel HEX.

### 4.1 Разберите назначение артефактов

Каждый созданный файл служит собственной задаче.
Используйте вариант, соответствующий инструментам в вашей лаборатории или производственной линии:

| Артефакт       | Типичные инструменты                                         | Когда выбрать |
|----------------|---------------------------------------------------------------|---------------|
| `.bin` (сырые данные) | Device Firmware Upgrade Utility (`dfu-util`), `dfuse-tool`, STM32CubeProgrammer (USB — Universal Serial Bus) | Основной выбор для обновлений на месте через USB DFU. Соответствует структуре, ожидаемой `make flash`, и пакетам `.dfu`, публикуемым в релизах. |
| `.hex` (Intel) | ST-Link Utility, STM32CubeProgrammer (интерфейсы Serial Wire Debug (SWD) / Joint Test Action Group (JTAG)), стенды производственного программирования | Требуется, когда программатор принимает только файлы Intel HEX (текстовый формат) или когда необходимы адресные метки для ручного анализа. |
| `.elf` (отладочный) | GNU Debugger multi-architecture (`gdb-multiarch`), Open On-Chip Debugger (OpenOCD), Lauterbach, аппаратные отладчики | Содержит таблицы символов и метаданные секций. Используйте для пошаговой отладки, формирования файлов `.map` или исследования сбоев. |

Релизные сборки в GitHub публикуют тот же набор файлов для всех четырёх вариантов.
Их можно прошивать без локальной пересборки.
Пакеты `.dfu` на странице релизов содержат файл `.bin` вместе с метаданными USB, чтобы такие инструменты, как Windows DfuSe, сразу распознавали образ.
Прошивка через `make flash` или `dfu-util` возможна как с исходным `.bin`, так и с артефактом `.dfu`.

### Аппаратные варианты ZeeTK

CI и релизные сборки предоставляют `F072`, `F072-ZK`, `F303` и `F303-ZK`.
Микроконтроллер по-прежнему выбирается через `TARGET=F072` или `TARGET=F303`,
а микшеры ZeeTK NE602A выбираются отдельным параметром `RF_PROFILE=ZK`:

```bash
make clean
make -j$(nproc) TARGET=F072 RF_PROFILE=ZK
make clean
make -j$(nproc) TARGET=F303 RF_PROFILE=ZK
```

По умолчанию используется `RF_PROFILE=STANDARD`. Имена стандартных образов:
`H` и `H4`; имена ZK-образов: `H-ZK` и `H4-ZK`. Отображаемая версия ZK-прошивки
также получает суффикс `-ZK`. Для каждого варианта релиз публикует файлы BIN,
HEX, DFU и контрольные суммы SHA-256 с отдельными именами.

Выбирайте ZK для NanoVNA-H rev3.7 и NanoVNA-H4 rev4.4 с микшерами ZeeTK NE602A
и синтезатором SJWCH5351. Усиление, гармонические диапазоны и токи выходов
соответствуют hugen79/NanoVNA-H 1.2.50 и предложению @jebcampbellhm в
[PR #12](https://github.com/momentics/NanoVNA-X/pull/12), связанному с
[запросом #10](https://github.com/momentics/NanoVNA-X/issues/10).
PR #11 посвящён среде выполнения и USB, а PR #13 содержит исправления вычислений,
хранения данных и обработки ошибок. Они действуют и в стандартных образах,
с адаптацией к уже имеющимся механизмам синхронизации NanoVNA-X. Авторство
сохранено в исходниках и регрессионных тестах. Выбор ZK меняет параметры
RF-оборудования, а не включает эти исправления.

У микшера нет программно считываемого идентификатора. В рассмотренных предложениях
также нет проверенного способа различить регистрово совместимые синтезаторы по
идентификатору устройства. Ответ на запрос I²C не позволяет определить микшер
или модель синтезатора. Стандартные образы сохраняют выбор Si5351, MS5351 и
SJWCH5351 во время работы через **System > Device > More > Mode**; сохранённые
идентификаторы 0, 1 и 2 остаются прежними. Образы ZK принудительно используют
параметры ZeeTK даже при наличии сохранённой конфигурации старого варианта.

Суффикс синтезатора сам по себе не определяет ревизию микшера. Сохранённые
RF-настройки загружаются до инициализации генератора. После смены варианта
прошивки или оборудования выполните калибровку заново. Точность RF-измерений
и время установления требуют отдельной проверки на реальной плате.

## 5. Бюджеты памяти и опции

Компоновщик ограничивает образ прошивки областью до сохранённых калибровок
и проверяет размещение статической памяти в регионах микроконтроллера:

| Цель | Бюджет флэш-памяти прошивки | Начало области калибровок | Основная SRAM | Отдельная CCM RAM |
| --- | --- | --- | --- | --- |
| F072 | 98 КиБ | `0x08018800` | 16 КиБ | Нет |
| F303 | 114 КиБ | `0x0801C800` | 40 КиБ | 8 КиБ |

Это пределы регионов, а не измеренные размеры прошивки или объём свободной памяти.
Область CCM размером 8 КиБ у F303 отделена от основной SRAM размером 40 КиБ;
их нельзя считать единым регионом. Успешная компоновка не доказывает достаточный
запас стека во время работы: для этого нужны отдельные измерения и анализ.

Команда `dump [selection]` включена по умолчанию на обеих платах. Она выводит
сырые отсчёты аудио АЦП через существующий рабочий буфер дисплея, без нового
массива отсчётов. Ожидание DMA ограничено двумя секундами. В собственной
конфигурации её можно отключить определением `ENABLED_DUMP_COMMAND=0`;
стандартная сборка F072 использует LTO, чтобы уложиться в бюджет.

В файле `Makefile` определены флаги компиляции `UDEFS`. Из-за ограничений памяти
(особенно на STM32F072) некоторые функции могут быть отключены по умолчанию.

### Конфигурация для F072 (NanoVNA-H)

Из общих 128 КиБ флэш-памяти F072 под прошивку доступно 98 КиБ; остальное
зарезервировано под сохранённые данные. Применяются следующие настройки:

- **Включено:** `__VNA_Z_RENORMALIZATION__` (Поддержка 75 Ом и смены импеданса).
- **Включено по умолчанию:** `ENABLED_DUMP_COMMAND` (команда `dump` передаёт сырые отсчёты аудио АЦП по USB; стандартная сборка F072 использует LTO, чтобы уложиться в бюджет флэш-памяти).
- **Отключено:** `VNA_AUTO_SELECT_RTC_SOURCE` (Автовыбор источника часов LSE/LSI).

### Конфигурация для F303 (NanoVNA-H4)

Для F303 по умолчанию включены следующие возможности:

- `__VNA_Z_RENORMALIZATION__`
- `ENABLED_DUMP_COMMAND`
- `VNA_AUTO_SELECT_RTC_SOURCE`

## 6. Прошейте устройство (по желанию)

Переведите оборудование в режим Device Firmware Upgrade (DFU) и прошейте созданный двоичный файл с помощью Device Firmware Upgrade Utility (`dfu-util`):

```bash
export TARGET=F072
make flash
```

Цель `flash` использует двоичный файл из `build/` для выбранной платы и
RF-профиля. Для ZK передавайте тот же параметр, что и при сборке:

```bash
make TARGET=F072 RF_PROFILE=ZK flash
```
Устройство должно определиться на хосте как интерфейс DFU; подробности о переходе в этот режим приведены в основном файле README.

## 7. Устранение неполадок

- **Компилятор недоступен** — убедитесь, что `arm-none-eabi-gcc` находится в переменной `PATH`, и установлены перечисленные пакеты.
- **Старые артефакты сборки** — выполняйте `make clean` при смене платы, `RF_PROFILE`, `USE_LTO` или компилятора, чтобы не смешивать несовместимые объектные файлы.
- **Ошибки доступа при прошивке** — в Linux добавьте правила udev для устройств DFU или запускайте `dfu-util` с `sudo`.
- **ПК не видит устройство** — после прошивки откройте USB-консоль и проверьте приглашение `ch>` перед баннером. Старые версии программ, например NanoVNA-Saver, могут потребовать переподключения, чтобы обновить сохранённое состояние соединения.

Следуя этим шагам, вы получите воспроизводимую сборку как локально, так и в средах непрерывной интеграции (CI).
